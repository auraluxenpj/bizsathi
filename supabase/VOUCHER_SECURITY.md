# Controlled journal and expense vouchers

## Scope and controls

The accounting workspace now records journal vouchers and rent/utilities/operating expenses using only bank, wallet and those three expense accounts. Cash, tax, invoice control accounts, sales/purchases and inventory are deliberately excluded. All entries post into the existing journal. Voucher metadata, journal lines and audit evidence are immutable; no new stock or invoice changes occur.

Posting uses authenticated accountants or higher trusted roles, explicit branch access, a shared business lock and an open-period row lock. The database validates finite two-decimal amounts, one-sided lines, 2–50 lines and exact positive balance. Expense vouchers debit expense and credit bank/wallet. The application never writes financial tables directly; default grants are revoked and branch-scoped SELECT RLS applies.

Voucher source IDs are generated by the database independently of client request IDs. Existing journal sources are checked for collision; a source guard prevents non-voucher entries reusing voucher IDs and checks voucher business/branch/period/date/actor/account attribution. Idempotency is unique per business/request with exact original-payload and actor replay checks. Audit headers include the immutable original request/lines, while public report snapshots exclude requests. Restricted function search paths and explicit execution grants are preserved.

Administrators/owners may fully reverse only these vouchers, never an invoice/payment/counter. Reversal date must be on/after the original and in an open period; original and reversal must share branch/business. The database derives every opposite line, ignores no partial adjustments and rejects caller-supplied lines or unknown fields. Original row locking, business serialization and a unique reversal link protect against duplicate reversal; reversal-of-reversal is denied. Original history is retained.

## Retry and report behavior

Before a call, the browser saves the unchanged request per user/business in session storage. Confirmation clears it; uncertain responses retain it for authenticated status checks or unchanged retry. Explicit cancellation first checks status. Corrupt/unreadable retained data blocks new entry rather than silently deleting it. This is online-only; tab/device storage loss is not guaranteed recoverable. Inspect immutable voucher history and original reference before recreating an interrupted request.

Reports include all 13 account codes, voucher references, expense debit/credit activity and negative expense reversals. Source evidence uses the same journal snapshot; there is no parallel ledger. Bank/wallet totals remain unreconciled, and opening balances/profit/full statements remain unavailable.

## Executed verification

- 61 unit/routing tests passed, including 22 voucher cases for allowed/protected accounts, exact balance, finite precision/size, one-sided lines, expense direction, strict reversal input, dates/evidence, per-user retry keys and expense/reversal report integration.
- Dedicated isolated PostgreSQL voucher tests passed for accountant posting, identical/conflicting retries, exact reversal lines, period/branch/tenant/role protections, immutable/audited history, snapshot inclusion, failed-write rollback and anonymous denial. Protected accounts, actor spoofing and caller reversal-line rejection are covered. Existing commerce, inventory, tenant, business-access and accounting suites were rerun and passed their rollback success markers.
- Signed-in browser checks confirmed forms, bank/wallet-only expense choices, journal line add/remove, expense-report selection, missing-prerequisite posting block, and 799×732 layout without page errors or horizontal overflow; signed-out access redirected to sign-in.
- The legitimate business has no branches/open periods or transactions. Successful live confirmation, reversal, retained-failure retry, populated evidence, CSV and print read-back remain **unverified**. No live sample transactions were created. High-volume multi-session concurrency/load assurance still needs dedicated review; database locking/uniqueness is a safeguard, not certification.

## Recovery and remaining work

Never edit/delete a posted voucher. Check the request/reference and history first after uncertainty; replay unchanged to avoid duplicate posting. Use one authorized full voucher reversal in an open period for corrections, retaining the reason and original link. Do not use vouchers to fix cash counts, stock, tax or outstanding invoices. Stop voucher posting if evidence is inconsistent and preserve records for review. Opening balances, custom accounts, cash expense integration, payment reversals, variance decisions, costing/COGS, full statements and offline POS remain separate reviewed increments. No deployment or paid integration was performed.
